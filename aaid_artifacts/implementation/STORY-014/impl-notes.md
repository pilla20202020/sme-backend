## Implementation notes

**Transactional scope matches the PRD's four-things-at-once list exactly**, all inside one `prisma.$transaction(async (tx) => { ... })`: (1) `tx.stockReceipt.create` + `tx.stockReceiptLine.create` per line, (2) `tx.productBatch.create` per line (quantityReceived/quantityRemaining both set to the receipt line's quantity — STORY-008's model, not duplicated), (3) `tx.purchaseOrderLine.update({ data: { quantityReceived: { increment: ... } } })` per line, (4) a fresh `tx.purchaseOrderLine.findMany` + `tx.purchaseOrder.update({ data: { status } })`. This is the first *interactive* (callback-form) `$transaction` in this codebase — every prior one (`ProductsService.updatePrice`, `CatalogImportService`'s price-change path) used the simpler array form, which doesn't support the read-after-write-before-next-write sequencing this story needs (compute discrepancies from a fresh read, then write, then read again to recompute status). Chose the interactive form deliberately rather than trying to force this into the array form.

**Discrepancy rule, read literally off the PRD**: a discrepancy is recorded whenever a receipt line's own `quantityReceived` doesn't equal `quantityOrdered - quantityReceived` (the line's outstanding amount *before this receipt*) — this covers under-receipt, over-receipt, and (deliberately) an ordinary planned partial delivery that isn't the line's full remaining outstanding amount. A judgment call worth flagging explicitly: the PRD's business-rules text supports two readings — the narrower one on the AC bullet ("under/over-receipt is flagged") and the more literal one buried in the discrepancy-fields sentence ("any receipt event where the receipt-line's own quantityReceived differs from the remaining ordered-minus-already-received amount"). I implemented the literal reading, since the API has no separate "planned amount for this specific event" field to distinguish "this is intentionally a partial shipment" from "this under-delivered" — the system genuinely can't tell those apart, so it surfaces the numbers every time they don't match rather than guessing intent. Concretely this means: the first of two sequential partial receipts (60 of 100) *is* reported as a discrepancy even though it's a perfectly normal planned partial delivery, not a mistake — this is intentional per the literal PRD wording and confirmed against both the mocked unit tests and the live smoke test.

**`productId` on a receipt line is derived, never caller-supplied.** `CreateStockReceiptLineDto` has no `productId` field — the API contract only asks for `purchaseOrderLineId`, and the service looks up `poLine.productId` from the referenced (already tenant/PO-validated) `PurchaseOrderLine`. This closes off a class of bug where a caller could claim a batch belongs to a different product than the PO line it's tied to.

**Validation is split deliberately: pre-transaction checks fail fast, in-transaction reads stay fresh.** PO existence/tenant match, `purchaseOrderLineId` membership, and past-`expiryDate` rejection all happen *before* `$transaction` opens — there's no reason to open a transaction only to immediately abort it for input that's already knowable to be invalid, and this keeps the 404/400 error paths simple to test without touching the mocked `$transaction`. The discrepancy computation and status recomputation, by contrast, happen *inside* the transaction against a freshly-read snapshot (`tx.purchaseOrderLine.findMany`), not the pre-transaction snapshot — necessary for correctness across genuinely sequential multi-event receiving (verified live and in the real-DB test), though see the concurrency caveat below.

**Known limitation, disclosed rather than silently accepted**: under true *concurrent* receiving (two `POST .../receipts` calls landing at almost the same instant against the same PO), the discrepancy numbers reported in each response are computed from a read taken at the start of that transaction — Postgres's row-level locking on the subsequent `UPDATE` guarantees the persisted cumulative totals and final status are always correct (no lost updates, since `increment` is atomic and status is recomputed from a fresh read after all increments in that transaction), but the *discrepancy explanation* in one response could reflect a slightly stale "outstanding before receipt" figure if another transaction committed in the narrow window between the read and the write. This is the same class of trade-off already accepted elsewhere in this codebase (no `SELECT ... FOR UPDATE` pattern exists anywhere yet); the acceptance criteria and the required smoke test both describe *sequential* multi-event receiving, which this implementation handles correctly with no caveats.

**Rollback-on-failure was not separately forced-tested.** Prisma's interactive `$transaction` is documented to roll back entirely if the callback throws; this codebase's only prior `$transaction` usage (`ProductsService.updatePrice`) likewise never forces a mid-transaction failure in its own test to prove rollback — I followed that same precedent rather than introducing a new testing pattern for this one service.

## Judgment calls (flagged explicitly, not silently decided)

1. **Discrepancy rule breadth** — see "Discrepancy rule, read literally off the PRD" above. Implemented the literal (broader) reading; a narrower "only flag genuine mismatches, not planned partials" reading would need a new field the current API contract doesn't have (e.g. an expected-this-event quantity), which the PRD doesn't ask for.
2. **Receipt-line `unitCost` is independent of the PO line's frozen `unitCost`** — the PRD's schema gives `StockReceiptLine` its own `unitCost` field distinct from `PurchaseOrderLine.unitCost`, and the API contract's receipt-line body includes `unitCost` separately. Interpreted this as: the receipt can record the actual invoiced/received cost (which may differ from what was originally ordered at), without ever mutating the PO line's frozen value — consistent with STORY-012's freeze rule. Not explicitly called out as intentional in the PRD text, but follows directly from the two fields being modeled separately in the schema PRD itself provided.
3. **Concurrency caveat** — see "Known limitation" above.
